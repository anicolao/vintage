# Production path audit

Audited 2026-09-21: `feat/milestones-through-six`, commit `7808cb11d9b87192a614512529ca3ac64798ab87`, PR #11. This is a source audit, not a new live-provider test. No application behavior is changed by this report.

The live Firebase infrastructure persists real inputs and edits, but the shipped worker does not identify items, learn seller style, or retrieve market data. It returns a fixed jacket proposal and £48 recommendation. Labelling these results as samples does not satisfy the requirement for production functionality.

## What is real, and what is intentionally test/design data

- Google authentication, owner-scoped Firebase persistence, photo uploads, image normalization, example storage, device queues, edits, version/conflict checks and exact approval snapshots have actual implementations. Their existence does not make the generated content real analysis. This audit does not recertify their operational correctness.
- `tests/**` contains deterministic users, examples, prices, images and emulator setup. Those are isolated test inputs and belong in tests. `functions/fixtures/proposal.json` is different: it is directly imported by the shipped runtime provider.
- `src/lib/firebase-config.mjs` and `src/lib/firebase.ts` explicitly separate live and emulator builds; `scripts/warm-functions.mjs` targets local emulator startup. These are not hidden live authentication substitutes.
- `static/images/wardrobe.png` is decorative sign-in imagery, also reused as a test upload. Approved mockups in `UX_DESIGN.md` are design references. Neither is injected as a seller's photo in the application.
- Empty-state labels such as Untitled item, input hints, skeletons, icons, theme tokens, validation limits and accessibility alternatives are ordinary UI behavior, not invented item data. Home cards are derived from account listings, not a seeded demo catalogue.

## Recommended replacement order

1. Replace the sample-only contracts and wire real style learning plus image/context generation as one complete path (1–4, 7–8). Keep the existing durable queue and optimistic editing. Reject runtime fixture results; do not keep a sample fallback. Completion requires demonstrably input-dependent results and persisted provider provenance on live Firebase.
2. Replace the £48 recommendation with evidence-backed pricing and supported currency, then implement the market/estimate views (5–6, 11). An unavailable state must describe a real retrieval/validation outcome, not a permanent stub. No fabricated probabilities or comparables.
3. Finish the output boundary and UI in the same delivery: actual progress, evidence/uncertainty, approval/copy and handling of existing sample records (9–10). Reopen unsupported completion claims and verify real integrations, with deterministic fixtures restricted to tests (12).

PR #11 should not be treated as production-complete while these P0 paths remain. The existing delivery notes acknowledge samples, but that qualification does not close the functionality gaps.
